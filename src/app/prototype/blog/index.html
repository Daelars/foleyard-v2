Read the full article

We've been rebuilding the way Foleyard handles tags. The next update introduces machine-made tags, but every one of them carries its provenance, and nothing lands on your files without either your explicit accept or a tool you switched on yourself.

That second half matters more than the first. A tag you can't trust is worse than no tag at all.

Born from a rejected pitch

This feature almost didn't exist. On the night of September 6th, three extension concepts were prototyped and two were thrown out as useless. The survivor was a "MAYBE": a coverage board that could live inside an auto-tagging extension, tagging indexed files in the background while switched on and keeping score on the board. That maybe became the brief: show which files are being tagged, what tags they get, and how the run went, with charts. Every layer below descends from that night. The trust model wasn't a constraint added later. It was the price of admission for a feature that started on probation.

Where Foleyard is heading

Tags used to be plain strings on files. Nothing recorded who made a tag: you, a filename rule, or a model. The next release changes that foundation. Every tag attachment now carries an origin (manual, deterministic, or semantic_ai) plus a confidence value, and manual tags win on read without extra work.

That origin flows from the database through the extension system into the library UI. Tags in file rows carry small M / D / AI marks, and an origin filter (All, Manual, Rules, AI) spans the library. If the machine gets something wrong, you can see it was the machine, and revert by origin in bulk.

The problem

The brief was simple: indexed audio should gain tags automatically, quickly, and in the background. Switchable, and off by default. Typing tags for hundreds of files by hand doesn't scale. Silent background writes don't build trust either.

So we built three layers with three different trust levels.

LayerWhat it doesWhat gates it
Deterministic rulesSeed rules over filenames and metadata, previewed before anything writes; every write marked deterministicTool enabled and approved; preview first
Candidate queuePaged suggestions, no writes while you browse; promoting attaches as manual, dismissing is rememberedYour explicit accept or dismiss
Semantic taggingModel-backed tags over an approved vocabulary, consent-gated downloadOpt-in, approved vocabulary, confidence bar

What we built

Deterministic rules. The new auto-tag-v2 tool ships seed rules over filenames and existing metadata, with a preview step before anything writes. Every write it makes is marked deterministic. The tool registers disabled by default. It changes nothing until you enable it and approve its permissions.

A candidate queue with an accept step. Suggested tags sit in a paged queue that performs no writes while you browse. Promoting a candidate creates (or finds) the tag and attaches it as manual. Dismissing one records that decision so it stops coming back. Words you've already tagged leave the queue on their own.

Similarity over stored vectors. A model-keyed embedding store with cosine ranking backs a "find similar" entry on file rows, with an explicit unavailable state when there is nothing to rank yet. Moving files preserves origins and vectors instead of silently dropping them.

A trigger that respects the off switch. When a scan completes, Foleyard submits chunked, idempotent tagging jobs, but only when the tool is enabled and approved. Unchecked background work was never on the table.

Opt-in semantic tagging with a visible seam. Model status, a consent-gated download with progress and cancel, and semantic tagging over an approved vocabulary. The inference backend is an explicit seam in the code. Honestly. The download, the trigger, the queue, and the board are real. Production model inference is not finished. The current development builds rank stub vectors. We'd rather say that plainly than let a screenshot imply otherwise.

A board to watch it work. The auto-tag board runs on real extension data, with coverage trends, sparklines, latest arrivals, goals, and origins styling. An early prototype had a cramped three-pane block and short accent zones with too much blank space. We collapsed it toward one pane with horizontal separators, ran the accents full-length, and moved the filter tags where they belong. The current board is the result of that critique, not the first draft.

Questions readers ask

Will auto-tag change my files without asking?

No. Rules need the tool enabled and approved plus a preview. Queue suggestions need your accept. Semantic tagging is opt-in.

What do the M, D, and AI marks mean?

Who made the tag: you (manual), filename rules (deterministic), or the model (semantic AI). You can filter and bulk-revert by origin.

When does this ship?

In the next release, unreleased as of this writing. The trust model is settled; model behavior and thresholds are still moving.

What is still changing

The model side is still moving. Vocabulary governance, thresholds, and which vector backend (if any) earns the job are open questions. The board layout isn't frozen either. What is settled is the trust model: origins on every write, explicit accept where it counts, disabled-by-default everywhere else.

Provenance first, automation second

The next Foleyard update won't just tag more of your library. It will tell you who tagged what, let you filter and revert by that answer, and keep the clever parts switched off until you ask for them. Provenance first, automation second. That order felt right, so we kept it.

The largest architectural change in our current development builds has no visible surface. We've rebuilt Foleyard's extension system as v2, with new contracts, registry, jobs, permissions, and transport, and shipped six v2 ports of the existing tools disabled by default. Run the branch with everything left off and nothing changes. That's deliberate.

Where Foleyard is heading

v1 (ships today)v2 (on the branch)
RoleThe product surface: routes, settings, dataInternal reference ports alongside v1
ToolsSix tools, wired inSix ports: Make Pack, Sound Shelf, Smart Collections, Folder Janitor, Library Gatherer, Drop Rules
Switching onAlready onSettings toggle plus permission approval, per tool
Switching offn/aRejects new work, cancels live jobs, removes UI after owned work settles
Settingsv1 namespacesSeparate namespaces; nothing migrates

A per-tool cutover will need its own compatibility and rollback plan later. That plan doesn't exist yet, and we're not going to pretend otherwise.

The alongside strategy has a cost, and the proposal names it: while v2 is built, v1's known gaps stay exactly where they are. Testing reproduced them firsthand. The Janitor silently truncated scans at 5,000 files. markRemoved accepted a permission the architecture guide doesn't describe. Those aren't v2's problems to solve, but they are the release's problems, and they wait on migration. An honest rebuild lists what it leaves behind.

The problem

The old extension paths grew organically. Execution spread across call sites, filename and matching logic duplicated per tool, settings persisted in slightly different ways. The repo audit put it bluntly: extensions and indexing were weak. The fix wasn't another feature. It was a contract.

From scratch, not on top

The rebuild began as a question about ratings: how much better could the system be, on a scale of one to ten, and what would a ten look like? The answer became the method. Improve the actual system first, then migrate the tools onto it. Build v2 from scratch rather than on top of v1. Rebuild one existing extension as the reference example. Touch every surface, docs included. That's exactly what happened: contracts and registry first, Make Pack as the reference port, then the other five, each with a parity table and migration notes. The quietest part of this release had the most deliberate brief.

What we built

V2 starts with API contracts and a serializable catalog, then a registry that only serves what the contract allows. Invocation goes through one path with availability checks. One place answers "can this run here, now?" Permissions are declared up front and approved explicitly. Jobs carry progress, cancellation, and recovery instead of fire-and-forget calls. Preview, review, apply, settings, state, and events round out the lifecycle, with UI contribution adapters so tools can add surfaces without reaching into the app.

Make Pack was rebuilt first as the reference port, then the other five followed, each with a parity table in its README recording what matches v1 and what doesn't. One limitation survived review and is recorded rather than hidden: the run-button behaviour has a known gap. It will matter at cutover time.

The same branch of work carried three quieter fixes: a single frozen IPC channel registry with payload validation at every send site, a chunked reader backing hydration and removal paths (one transaction per batch), and canonical filename behaviours in yard-core that the ported tools now share instead of reimplementing.

What we tried first

We prototyped three brand-new extension concepts as interaction studies. Full single-file mockups, explicitly not to be merged. The feedback kept one direction (the "sound rack" idea with ranked shortlists and library candidates) and deleted the other two for feeling clunky and bloated. That exercise never touched the app, but it sharpened what a v2 tool surface should feel like.

What made the cut

Everything above already runs in our development builds. You just can't see it until you switch a port on. Discovery asserts all six v2 identities, the workbench and inspector exercise them with fixtures, and verification plus release notes cover the ports as a set.

Questions readers ask

When does v1 go away?

No date exists. A one-shot removal plan was written, reviewed, and rejected the same night. Cutover, if it happens, goes one tool at a time with parity proven and a way back.

If I enable a v2 port, does it import my v1 settings?

No. The namespaces stay separate. That is a cutover problem still to solve, not a detail.

Quiet on purpose

V2 adds no user-facing feature today. It adds the ground the next features stand on, including auto-tag, which is built as a v2 tool from the start. When the cutovers come, they'll come one tool at a time, with parity proven and a way back. Until then, the rebuild stays quiet on purpose.

Before the next Foleyard library settles, it went through a reskin, a port, and a whole showcase of competing visual directions. Most of them lost. That's the story.

The setup

The reskin ran like a machine, because it was run like one. A wayfinder map set the destination, a binding token law set the rules, and the work moved one ticket at a time, lowest number first, each on its own branch. That machinery is why the reskin reads as systematic instead of inspired: it was systematic on purpose.

It started with tokens: land the theme law first, then bring every surface into one language. Header, sidebar, library list, transport player, Sound Shelf, dialogs, settings, onboarding. Each moved in its own pass. Then came the port track: app shell with icon rail, selection model and bulk bar, transport queue and console, command palette, shortcuts with conflict resolution, row waveforms, palette glow, filter menus, nav flyouts. Finally the Organize view consolidated collections and tags browsing, with rename and color helpers.

Alongside all of that ran the Showcase: five designs each for palette, flyout, rows, and console, then revised palettes, popups, consoles, organize flows, artwork washes, radial headers, and the W-D through W-K scrim and motion studies.

And behind the ticket machine sat a pixel law. Spacing had to stay consistent (mt-4 meant mt-4 everywhere), boxes had to fit their content dynamically, sidebar margins were policed, and the organize animation had to match the prototype frame for frame. The kind of review that reads as fussy is what makes a reskin hold together at every zoom level. This one had it, in blunt terms, daily.

Functionality, meanwhile, was frozen. The audit brief said keep it exactly the same, and anything that moved behavior got reverted: a loading spinner in the wrong place, a library view suddenly too big. The reskin changed how everything looks and nothing about what anything does. That separation is why it could move at ticket-machine speed without breaking the app underneath.

Prototype A: everything at once

The full app-v2 mock wired the winning designs together end to end. It looked coherent in isolation. As part of the full library, pieces of it didn't survive. Normal. That's why the mock existed.

What didn't work

The W-G minis file is the cleanest example. Removed outright and replaced by fresh W-H, W-I, and W-J takes: a rail-detail layout with a fixed inspector, full-feather scrims, action buttons following the chosen color. We can show you the sequence. We won't invent a motive beyond it, because the decision wasn't written down. Sometimes a direction just reads wrong once it's next to everything else.

Smaller reversals happened too. Settings gained display-scale section titles for hierarchy, then lost them the next day. A tag editor lived on the filter pill, then decoupled from it, then settled where it dismisses on any outside interaction. Each step is in the history if you want the full flip-book.

Read the full article

We deleted most of Foleyard's test suite on purpose. The next release is covered by around fifty integration tests instead of hundreds of unit tests, and the coverage means more, not less.

The problem

The audit prototype told the story before we felt it: the repo carried roughly four hundred tests (the track's own count: 410), and nobody could say what they proved. The request that followed was blunt. There's no way there should be that many, cut down significantly, why can't we have maybe fifty. Then the harder question: what's the before and after?

A parallel slop hunt said the same thing from the other side: useless tests, unnecessary wrappers, weak extension and indexing coverage. Count wasn't the disease. It was a good symptom.

What we did

First we collected every test file on disk and published a coverage baseline, so the before picture existed in writing (docs/audit-2026-09/ holds the inventory, findings, and results). Then we built an integration harness targeting roughly fifty tests and rebuilt eight areas against it:

  • filesystem grant boundary (8)
  • data-loss prevention (8)
  • database correctness (8)
  • extension host and transport (8)
  • scanner (6)
  • client mutation lifecycle (5)
  • desktop and supply chain (5)
  • component and layout smoke (2)

Plus the yard-core service decision and CI gating the full verification set.

The old unit suites were deleted. The history shows route-level, hook-level, and component tests going out in bulk. Sixteen expected-to-fail regressions were pinned against live defects at the time, so the new suite started by admitting what was still broken.

Why integration tests

Unit tests kept proving that isolated functions worked in isolation. The bugs that bit us lived at boundaries: grants on routes, scan phases, shared SQLite handling, host transport, mutation lifecycles. Those are integration facts. Naming helped too. Test names now state what they prove, and CI refuses to pass without the full set.

Questions readers ask

Are unit tests gone forever?

The old suites were deleted in bulk. The integration suite in src/test/integration/ is the coverage now, and CI gates on it.

Why roughly fifty?

That was the target set before the rebuild started: enough to cover every boundary that had actually bitten us, few enough that each test has to earn its place.

What does this prove about the release?

When the hardening posts say "verified," this suite is the verification: files, scans, extensions, the database, and the desktop boundary, on every push.

Fewer tests, stronger promises

Fewer tests, stronger promises. The suite fits in one directory, runs in CI on every push, and covers the paths users actually hit: files, scans, extensions, the database, the desktop boundary. When we say the hardening work below is verified, this is the verification we mean.

Full text: blog-posts/posts/getting-ready-next-release/index.md

Read the full article

The branch has the features. The question since then has been whether it holds together. Recent work split three ways: correctness first, then scan and waveform performance, then contracts. Here's where each stands. Done, still moving, and explicitly not promised.

Done: the revisions hardening

The revisions track worked through the open-ticket backlog on its own branch before merging: filesystem grants connected and enforced on the remaining routes, directory navigation unified, extension registration from data, mutations validated with shared API responses, one SQLite connection shared across routes and extensions, scan metadata preserved with separated phases, the Janitor scanning every indexed file in its folders, the file repository split into reads, writes, and batches, extension vocabulary consolidated, JSON setting persistence shared, and the dot-matrix math split from its rendering.

None of that shows up in screenshots. All of it shows up in reliability.

Done: scan and waveform performance

Scans got two changes that compound. Unknown files now get a full metadata parse in the same job instead of churning through a second pass, and concurrency widened (metadata 8 to 16, per-batch stat fan-out 8 to 32). Waveform rendering moved to browser Web Audio decoding in parallel, with an IndexedDB plus memory cache. The in-flight decode was detached from any single row's abort signal, so scrolling away mid-decode no longer fails the decode the remounted row is waiting for. The server waveform endpoint stays as the fallback for formats the browser rejects.

Done: contracts

Extension invocation, file hydration and removal, filename handling, and desktop IPC each got a single choke point: a typed channel registry with payload validation, a chunked reader doing one transaction per batch, canonical filename behaviours in yard-core adopted by the ported tools. The Gather tool leaves pre-existing destination files intact rather than failing the run. A small decision that prevents real data-loss scares.

Still moving

Auto-tag follow-ups continued past the current HEAD: model behaviour, board layout tightening. Several prototype routes (app-v3, component library, variant library, performance explorations) remain open design questions. They may shape the release. Nothing there is decided.

Explicitly not promised

Removing the v1 extension system exists as a written plan (cut over to v2 first), not an execution. Evaluating which TanStack libraries (if any) would help live UI updates is a plan for a plan. Real model inference and any specific vector database are researched, not shipped. The builds rank stub vectors through an explicit seam. No version number, no date.

Why this post closes the sequence

The arc of this series is the arc of the branch: auto-tag gives the release its headline, v2 gives it its foundation, the discarded designs give it its honesty, the test rebuild gives it its proof, and this hardening gives it its chance to hold together. A week after reskinning Foleyard, we put its components themselves on trial. Ten variants, a glassy redesign imposed on a finished layout, corrections in all caps. Then the winning variant hardened into a real library, with the whole app rebuilt around it as app-v3. All of this is uncommitted prototype work. None of it is the new app. That's what makes it worth showing.

It started with a sentence. Asked what felt wrong with the app's controls, the answer came back: a bit of everything, they just don't feel like they make sense, especially with the glowy, transparent glassy type feel. That line became the whole program: controls that belong to a dark, translucent, glassy app, orange used sparingly instead of poured on.

One reference survived every round that followed: the Analyse with CLAP button. Inputs didn't match, tags didn't match, small buttons were hard to read, the palette was weak, but that button was right. So the trials became a search for everything else that could stand next to it.

The problem

The reskin brought every surface into one visual language, but the individual components never got redesigned to match. Pills, inputs, tags, small buttons that were hard to read, a weak command palette. Against the glowy, transparent glassy feel of the rest, the stock primitives looked borrowed. So we asked for a bespoke component library: a detailed prompt for another agent, researched by subagents, reviewed like a design commission.

The trial grid

VariantWhat it taught

COne token block, one accent source; glass as a system, not a coat of paint
DMatching a reference exposes every inconsistency a grid hides
ECorrection: components only, layout stays

The rule that stuck came out of B: great layout, but the next variant shouldn't have changed the layout at all, just the components. Components were the assignment; page design was settled.

When work strayed outside the prototype, it got reverted with feeling: you're only touching the prototype, undo that. Mid-trial regressions got reported the same blunt way. The popdown is gone. This still doesn't match the rest. The all-caps isn't embarrassment. It's a process with taste, enforced in real time.

A selection language, not a stylesheet

The deepest work of the trials wasn't colors. It was deciding that open select, command palette, and pagination-active all speak one selection language: red tint plus red edge plus faint glow for the chosen row, the same hover wash, the same row rhythm everywhere. Before that unification, the selected option read as a different, flatter component. After it, three surfaces agree with each other.

Same with states. Disabled used to wash everything to gray, which also made loading look dead. The trials split them on purpose: disabled stays readable through shape (sunken well, visible edge, no glow) while loading keeps full contrast with a wait cursor. Busy, not gone. The reasoning was accessibility first, aesthetics second: a faded label nobody can read isn't minimal, it's broken. Contrast ratios, keyboard paths, focus that never drops, reduced-motion fallbacks on every animated surface. None of that shows in a screenshot. All of it is why the components feel right.

Motion got the same treatment. An early pass choreographed whole pages: rising headers, cascading cards, drifting ambience. Then came the correction that defines Variant G: no page choreography. The motion lives in the elements. Buttons lift a pixel and squash to 0.97 on press. Switch thumbs travel on a spring with a little overshoot. Checkmarks draw themselves stroke by stroke. Alive controls, calm page. That distinction is the kind of thing you only learn by building the wrong version first.

Variant H came from auditing real usages instead of the component folder: tabs with a sliding pill, volume and zoom sliders with keyboard support, a real remove dialog, file-row menus. And the transport got rebuilt as a full shell with a live queue, scrubber, and a hero play button whose glow deepens while playing. Not the shipped 32px pill with new paint. The actual transport, taken seriously.

What survived the trials

Variant I. Extracted into a genuine reusable library with its own styles, components directory, entry point, README, and test. Not a mockup page but code another surface could import. A 30-piece kit of primitives grew up alongside it.

Then came the bold step: rebuild every surface of the app with the new components in the exact same interface as the real app. app-v3, a full prototype twin. Copy exactly was the instruction. A Variant J plan goes further, aiming the same component set at the real app's UI and data.

What is already breaking

The first app-v3 bug reports are in, and they're reported, not fixed: the auto-tag sidebar tab doesn't appear on enable until a reload, pagination is missing so lists run on forever, and the file lists under the charts show far too many rows. Read the full article

A week after Foleyard learned to tag itself on the branch, the feature met a real library: 16,000 files, 15,000 of them untagged. The result of the first serious run: CLAP tagged 0, attached 0, skipped 500. Nothing cleared the bar.

We're publishing that number because it's the most useful thing in this series so far. Features meeting reality and losing, on the record, is the whole point of documenting development instead of announcing releases.

The run, in numbers

  • Library: 16,000 files
  • Untagged: 15,000
  • Tagged by CLAP: 0
  • Attached: 0
  • Skipped: 500
  • Verdict: nothing cleared the bar

The opt-in model download works: the CLAP model files sit in the workspace, the consent gate, progress, and cancel all behave. But with thresholds and vocabulary gating set where they are, a 16k-file library produced exactly zero tags. We don't yet know whether the bar is too high, the vocabulary too narrow, the seam too lossy, or the model wrong for the material. The roast thread asked all of that ("roast our implementation, don't hold back… how could we make our own CLAP model, faster, better"), and the answers are still uncommitted work. Reporting the zero without a diagnosis is the honest state.

The questions the zero raised

Promoting candidates, deterministic-versus-manual notes, the origins display. Against a run that cleared nothing, all of it read as clutter. The board's second critique round was unsparing: the file-list and candidate navigation don't fit, the pills don't fit, and the prototype iterations weren't even mirroring the real UI. Then the sharpest question of the fortnight: why is origins on there at all?

That question deserved a real answer, and it got one. The rules are deliberately tiny: twelve seed tokens (whoosh, thunder, rain, and nine friends). Deterministic matching trades recall for precision. A file gets only what a rule fires, never a guess. So across 15,000 untagged files, nearly every filename holds words no rule covers, and the queue is where those words surface, aggregated with counts and example files. Promote one and dozens of files tag at once, as manual, optionally kept as a future rule. The vocabulary CLAP matches against grows with every accept. Dismiss one and it stays dismissed. Without the queue, the choice is hand-tagging 15,000 files or trusting guesses. The queue's job is real.

Its shape wasn't. Rendered twice (Coverage and origins tab both), twenty rows with pagination, Promote styled identically to Dismiss, the verbs disappeared into the furniture. That critique was agreed on the spot: one place not two, a summary row instead of twenty rows, top three with an expander, Promote as the only accent action and Dismiss as ghost. The minimal variant is that agreement, drawn.

Same with provenance. Asked whether the marks shouldn't be badges, the honest answer turned out smaller than badges: production marks are bare mono letters riding inside the tag itself, precisely so the badge count per tag doesn't triple. And the prototype mock had it wrong, wrapping each letter in its own pill, adding the exact chrome under objection. It got fixed to render the real component. A mock corrected by the thing it mocked. That's the process working.

One verdict already landed around the questions. The command-bar direction earned the one piece of outright praise in the whole critique, plus a concrete brief: smaller, one viewport, no scrolling. The fit variants are that brief, drawn.

What we're not doing

Lowering the bar until numbers look good. That would trade the trust model from the first post for a demo. Building our own CLAP model because a roast thread imagined it. That was a question, not a plan. Ripping out the queue or origins UI mid-question. The critique is recorded, the removal isn't decided.

Whatever the number is

The first post in this series promised provenance first, automation second. The second week tested the second half and found it wanting: the machinery runs, the download works, the jobs trigger, and the tags don't clear. That's an in-progress report, not a setback narrative. The release earns auto-tag when a real library run clears the bar with the trust model intact. We'll quote that run when it happens, whatever the number is.
