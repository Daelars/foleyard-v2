Foleyard extensions · before v2

How a tool ran in the old extension system

Every bundled tool took this route. It worked. The problem was the last box: the context offered a filesystem service, but nothing forced a tool to use it, so tools reached the disk directly.

Renderer
A surface fires a command
A button in the library calls executeHostedCommand() with the current selection.
→
HTTP
POST /api/extensions/execute
One route for every tool. Rejects a missing id or the wrong input shape.
→
Host
Registry lookup, enabled check
All six tools register at module level, then the host checks the id exists and is switched on.
↓
Core
Build the context
Library, tags, favorites, collections, settings, events. Handed over as one object.
→
Extension
The handler runs
Scope and selection validated, then the tool's own code does the work and returns an outcome.
→
Disk
node:fs, directly
Every tool treated the filesystem service as optional and fell back to raw fs with no library-root check.

The seam had no teeth

The context promised to resolve paths safely. Tools wrote if (services.filesystem && ...) and otherwise touched the disk themselves. Permission checks passed while a tool could still write anywhere.

Six tools, six habits

Filename cleaning, extension matching and settings persistence were re-implemented per tool, each slightly differently. Fixing one did not fix the others.

Nothing could report progress

A command was one call that either returned or threw. Long jobs had no progress, no cancel, and nothing to recover if the app closed mid-run.

Evidence: packages/yard-core/src/extensions/, src/lib/extensions/host.ts, and the September repo audit. This is the system Foleyard 0.1.8 ships.
