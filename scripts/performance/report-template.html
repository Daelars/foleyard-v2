Make browsing and previews faster.

Local benchmarks found gains in cache admission, PCM processing and SQLite queries. Here is the evidence and the TypeScript implementation plan.

There are worthwhile gains in TypeScript

Start with cache admission, a specialized PCM loop, then browsing indexes paired with cheaper unchanged-row updates. These are measured local experiments. Production changes are still to be implemented.

Indexing is already concurrent. More concurrency is not a clear win.

1,000 generated WAVs: new index 263.2 ms; unchanged 40.6 ms; 1% modified 44.7 ms. Outstanding metadata work reached 872 jobs including active work.

Metadata-only medians: 16 workers 201.0 ms, 32 workers 193.8 ms, 64 workers 225.0 ms. Keep 16 for now. A bounded queue controls memory; it is not a demonstrated throughput improvement.

Do the indexes slow down scans?

For 10,000 metadata updates, the scratch database took 26.0 ms with existing indexes, 26.7 ms with the filename index, and 84.8 ms with both proposed indexes. The duration index has a visible write cost.

Unchanged-row touches also maintain the new partial indexes because the current SQL rewrites removed_at. With both indexes, limiting a proven-unchanged touch to its timestamps reduced this batch from 237.5 ms to 40.8 ms. Pair that change with the browse indexes.

Rust verdict: defer the switch

The unchanged algorithm in a persistent Node worker took 173.5 ms versus 167.9 ms on the main thread. That is not a substantial throughput win. The specialized TypeScript loop is the stronger result. Rust was not benchmarked, so this does not establish how fast Rust would be.

Only reconsider a Rust worker after these changes if measured CPU or preview latency still misses your target. Worker event-loop samples here are inconclusive on Windows; idle timer scheduling makes them unsuitable evidence of a responsiveness win.

What these numbers cover

AMD Ryzen 7 5700X 8-Core Processor, Node v24.14.0, Windows. Three scan rounds; generally five repeats for the other cases. Generated audio and scratch SQLite only, warm OS cache. The PCM experiment handles canonical PCM16 stereo; it is not a replacement for the full parser. Browsing timings exclude HTTP, tags and rendering. Compressed audio was measured separately: one-minute MP3 155.8 ms, FLAC 150.5 ms. No cold-disk, network-storage or real-library measurements.

A cached waveform can wait behind a slow decode

The cache lookup currently happens inside the two-job generation limit. Checking the cache first would let valid hits return while uncached files are being processed.

A Rust queue can use Tokio bounded channels. That mechanism provides backpressure; it does not establish a speedup. Revalidate canonical paths at use time and keep the existing filesystem policy.
