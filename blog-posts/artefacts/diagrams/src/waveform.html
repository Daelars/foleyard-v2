Why waveforms stopped being instant, and how they got fast again

Drawing a waveform means decoding audio and reducing it to peaks. Where that decode happens decides whether a list of fifty sounds appears at once or one at a time.

Before — every row queued behind one decoder
Renderer
50 rows ask for peaks
A folder opens. Every visible row wants a waveform at the same moment.
→
HTTP
GET /api/waveform
Fifty requests to one route.
→
Server
One ffmpeg slot
Decoding is serialized. Row 50 waits for rows 1 to 49 to finish.
→
Disk
Cache warms slowly
The disk cache only helps the second time you look at a folder.
↓
After — decode where the parallelism already is
Renderer
50 rows ask for peaks
Same folder, same fifty rows.
→
Browser
Web Audio decodes them
Rows and the player decode in parallel in the browser and reduce to 512 peaks each.
→
IndexedDB
Keyed by mtime and size
Best effort only, with a bounded wait, so a cold or blocked cache never stalls a row.
→
Fallback
The server route, still there
Kept for formats the browser refuses to decode.

The fix was not a bigger cache

The brief was to make it feel instant with a cold cache, the way it used to, rather than to warm a cache harder. Moving the decode into the browser is what did that.

The scanner got the same treatment

A 443-line scan runner became separate discovery, metadata queue, progress and reconcile stages, so metadata is preserved across a rescan instead of being thrown away and rebuilt.

Source: src/lib/client-waveform.ts, src/components/AudioPlayer/use-waveform-peaks.ts, and the scanner split in commit 14ed665.
